# スキャン精度の評価

レシートスキャンの精度を、処理の段階ごとに測るための仕組みです。今の評価対象は「店名・日付・合計の抽出（`ReceiptParser`）」と「食材の抽出（`ReceiptFoodExtractor`）」です。

## 流れ

```
eval/data/<id>/receipt.jpg ──(端末: OcrDumpTest)──> ocr.txt, ocr_lines.json
eval/data/<id>/truth.json      ──┐
                                 ├─(PC: ScanAccuracyReportTest)──> app/build/reports/scan-eval/data/report.md
eval/data/<id>/ocr_lines.json  ──┘   (なければ ocr.txt)                                      summary.json
```

1. **撮影**：レシート1枚につき `eval/data/<id>/` を1つ作り、写真を入れます。ファイル名は自由で、拡張子は jpg・png・webp のいずれかです。
2. **正解を書く**：同じディレクトリに `truth.json` を置きます（形式は下にあります）。
3. **端末で文字認識**：実機かエミュレータを adb で接続し、次を実行します。
   ```bash
   eval/run_device_ocr.sh
   ```
   アプリと同じ ML Kit 日本語モデルで認識し、`ocr.txt`（ML Kit が返す文字列そのまま）と `ocr_lines.json`（各行の文字列と位置）を各ディレクトリに書き戻します。端末に送った画像は、終わったら削除します。
   評価では、アプリと同じく `ocr_lines.json` の位置から行を組み立て直した文字列を解析にかけます。`ocr_lines.json` がないときは `ocr.txt` をそのまま使います。
4. **PC で評価**：
   ```bash
   ./gradlew :app:testDebugUnitTest --tests '*ScanAccuracyReportTest*'
   ```
   `app/build/reports/scan-eval/data/report.md` に結果が出ます。ルールを直したら 4 だけを繰り返せば再計測できます。

`eval/data/` は **git に入りません**。レシートには購入履歴や店舗の位置などの個人情報が含まれるためです。リポジトリに入っている `eval/samples/` は動作確認用の合成データ4件で、画像はありません。

## アプリの検証モード

実際に使ったときの精度は、アプリの検証モードで測ります。設定画面の「スキャン精度の検証」で ON にすると、1枚撮影するたびに次を端末内（アプリ専用領域）に記録します。クラウドバックアップの対象からは外しています。

| ファイル | 内容 |
|---|---|
| `image.jpg` | 撮影した写真（ギャラリーから選んだ場合はその画像） |
| `ocr.txt`, `ocr_lines.json` | `OcrDumpTest` と同じ形式の認識結果。`ocr_lines.json` には行ごとの信頼度も入ります |
| `log.json` | 撮影時の判定スコア（明るさ・エッジ量・ブレ）、自動シャッターか手動か、アプリが読み取った値、ユーザーが保存した値、直した項目（`corrections`） |
| `truth.draft.json` | 保存した値から作った `truth.json` の下書き。見逃した品目と食品以外の品目は入っていないので、写真を見て足してください |

設定画面の「検証ログを書き出す」で ZIP に保存できます。ZIP には全体の `summary.json` が入り、項目ごとの**修正率**（保存したスキャンのうち、その項目を直した割合）が出ます。これが実際の使用状況での誤り率です。

ZIP の中のディレクトリを `eval/data/` にコピーし、`truth.draft.json` を確認して `truth.json` に名前を変えれば、そのまま評価データになります。連続撮影モードのスキャンは今は記録しません。

## truth.json

```json
{
  "id": "2026-10-01-maruetsu",
  "store": "マルエツ 新宿店",
  "date": "2026-10-01",
  "total": 1199,
  "conditions": { "lighting": "dim", "angle": "tilted", "wrinkled": true, "long": false, "device": "Pixel 8" },
  "items": [
    { "name": "ｷｬﾍﾞﾂ", "price": 198, "isFood": true, "category": "VEGETABLE" },
    { "name": "ｶﾙﾋﾞｰ ﾎﾟﾃﾄﾁｯﾌﾟｽ", "price": 148, "isFood": false }
  ]
}
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | | 省略するとディレクトリ名を使います |
| `store` | ○ | 店名。支店名まで書かなくても構いません。判定は「どちらかがもう一方を含むか」で行います |
| `date` | ○ | `YYYY-MM-DD` |
| `total` | ○ | 支払った合計金額（税込み）。完全一致で判定します |
| `conditions` | | 撮影条件。キーと値は自由で、レポートでは `キー=値` ごとに集計します |
| `items[].name` | ○ | **レシートに印字されているとおりに**書きます（半角カナは半角のまま） |
| `items[].isFood` | ○ | 冷蔵庫で管理する対象なら `true`。お菓子・飲料・日用品は `false` |
| `items[].category` | 食品なら | `VEGETABLE` / `MEAT` / `FISH` / `DAIRY` / `OTHER` |
| `items[].price` | | その品目の行に印字された金額。数量が2個以上なら合計額で、値引き行を引く前の金額です。書いた品目だけ価格の正解率に数えます |
| `items[].quantity` | | 数量。省略すると 1 です。今は評価に使いません |

`conditions` に使うキーの推奨値は次のとおりです。条件ごとの比較ができるよう、表記を揃えてください。

- `lighting`：`normal` / `dim` / `backlit`
- `angle`：`flat` / `tilted`
- `wrinkled`：`true` / `false`
- `long`：`true` / `false`（スクロールしないと収まらない長いレシート）
- `device`：撮影した端末名

## 指標

| 指標 | 定義 | 目標 |
|---|---|---|
| 店名 | 予測と正解のどちらかがもう一方を含めば正解（NFKC、かなの違いは無視） | — |
| 日付 | 完全一致。読めなかったときは今日の日付が入るので、不正解になります | 95% |
| 合計 | 完全一致 | 95% |
| 食材 適合率 | 抽出した食材のうち、正解の食材に対応づけられた割合 | 90% |
| 食材 再現率 | 正解の食材（`isFood: true`）のうち、抽出できた割合 | 85% |
| カテゴリ | 対応づけられた食材のうち、カテゴリが一致した割合 | — |
| 価格 | 対応づけられた食材のうち `price` を書いたものについて、抽出した価格が完全一致した割合 | — |

- 品目の対応づけは、正規化した名前の類似度（1 − 正規化レーベンシュタイン距離）が 0.6 以上のものを、類似度の高い順に1対1で組み合わせます。
- 適合率と再現率はマイクロ平均（全レシートの件数を合算）です。

## 集めるレシートの目安

50〜100枚を目標に、条件が偏らないように集めます。

- **店の種類**：大型スーパー（イオン、イトーヨーカドー）、地域スーパー、業務スーパー、コンビニ、ドラッグストア
- **撮影条件**：`lighting` × `angle` の組み合わせごとに最低5枚
- **しわのある・長いレシート**：それぞれ10枚程度
